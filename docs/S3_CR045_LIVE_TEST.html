Why the change looked invisible

The starting complaint was that applying CR-2026-045 in the console produced no visible difference in the app. Two independent causes, both confirmed:

#CauseEffect on stage
1 The post-apply link pointed at the wrong app. TARGET_APPS in useS3Controller.ts had an entry for ClaimsPortal only; every other target fell through to DEFAULT_TARGET_APP, the PolicyCore portal.
Fixed — an enroldirect-prospect-access entry now points at :8083.
 "Applied — open the policy portal" sent the presenter to an app CR-2026-045 does not touch. Nothing there changes, because nothing there was changed.
2 The target service serves the code it imported at startup. apps/run-enroldirect.sh ran plain uvicorn with no reload.
Applying rewrites .py files on disk; a running process does not notice.
 Even on the right app, :8083 keeps answering with the baseline while the console's diff insists the change landed.
The trap in its original form

In the session that prompted this test, the files changed at 14:53:06 and the EnrolDirect process had been running since 14:36. The change only became visible because the process happened to be restarted at 14:54:46. Had it not been, the run would have shown an applied diff and an unchanged app.

The subtlest before/after on the page

Pre-CR the catalogue offers this applicant two plans as available: true while the gate refuses them outright, and effectiveCategory is null. The catalogue and the gate are describing the same person differently. That is precisely the inconsistency the CR's last acceptance bullet closes — and it is visible without changing a single line of the console UI.

Three fields carry the CR's intent, not just the boolean: category still reports what the applicant is (PROSPECT), authorisingPreference reports what actually opened the gate (Guest), and prospectPolicyApplied records why those differ. A prospect admitted as a guest is recorded as such — which is what the CR requires for DocumentHub and NightlyBatch downstream.

This is the walkthrough's strongest single frame

The CR states the classification "decides two things, not one, and both are in scope… the two effects run in opposite directions". Here they are in one screen: the Guest policy admits Devon at the gate and narrows what Devon can reach past it. The refusal code moving from NO_CHANNEL_ACCESS to PLAN_REQUIRES_EXISTING_COVERAGE is the proof that AC2's "every existing refusal code keeps its current meaning" holds — the refusal moved from the gate to the catalogue, deliberately.

What this run does not evidence

  • The console's own Apply path. Step 6 copied the snapshotted files in directly, so what is proven is that the applied code produces these results — not that the console's Apply button wrote them. That path was exercised separately in the session that produced the snapshot.
  • The generated test suite. Not run here; the console still reported "the generated suite has not been run against this change yet", which is why the commit gate stays closed.
  • Source control. Nothing was committed or pushed by the pipeline — scm.py models branch/commit/push and runs no git, by design.
  • Any live LLM call. The whole run is replay/deterministic; no model was invoked at any step above.

Start EnrolDirect with TARGET_RELOAD=1 so step 2 lands without a restart — or restart :8083 by hand between steps 2 and 3. And the post-apply link in the console now goes to EnrolDirect rather than the policy portal; if you are running an older build, ignore it and go to :8083 directly.
