Stage 1
Impact analysis
AI does
  • Reads the story and the code together
  • Asks what the story leaves out, then sizes the job
  • Checks every system that depends on this one
A person decides
Answers the questions AI raised, then accepts the assessment.
You get
A written assessment, and a job raised for the one other team that must change code.
Stage 2
Target selection
AI does
  • Finds the right repository and narrows the file set
  • Marks the files it may read but not edit
  • Checks out a working copy
A person decides
Confirms the repository and file set before anything is checked out.
You get
A working copy, and an explicit list of files AI may touch.
Stage 3
Code generation
AI does
  • Works on a branch, never on main
  • Edits each file with a stated reason
  • Answers "why did you do that?", and writes the design document
A person decides
Reviews the diff, questions it, then approves or rejects — file by file.
You get
A reviewed change on a branch, plus a design document with a change map.
Stage 4
Test
AI does
  • Drafts a test plan from the acceptance criteria, then writes and runs the tests
  • Re-runs the existing regression suite
  • Traces each criterion to its test
A person decides
The tester approves the plan before any test code exists — and can fail the ticket back to the developer.
You get
Results, plus proof each requirement was checked and nothing else broke.
Stage 5
Release
AI does
  • Writes release notes for three audiences
  • Derives the go-live order from the change map
  • Writes the rollback steps and assembles the release record
A person decides
Approves the release and closes the ticket. Approvals are read from the ticket, not posted by a screen.
You get
A release note, a go-live and rollback plan, and a record that matches what happened.

What makes the claims checkable

GuaranteeWhy it is there
AI may never write to the regression suite Each application keeps a checked-in, human-authored suite that must pass before and after. A suite the pipeline can rewrite is not an independent check of anything.
The test plan is approved before test code exists Otherwise the tester reviews tests written to pass. They can also fail the ticket back to the developer.
Approvals and gates are read server-side "Tests passed" comes off the ticket's event log, never a flag a screen posts — a client that could assert it could commit a red branch.
Nothing overstates what happened The release record names what it did not prove, and source control is shown as commands a real integration would issue. Nothing runs git; no screen claims a deployment.
